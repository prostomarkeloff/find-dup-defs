# Do the work once per distinct input, not once per definition

**13.8× less CPU** (365 s → 26.5 s) and **4.6× wall** on a 371k-definition tree. Every report
byte-identical: ten output modes diffed against a binary built from `main`, 146 tests, clippy, and
the self-gate all unchanged.

One commit, 6 files, +1106 / −258.

---

## The observation

The profile said the time was in exact Ratcliff–Obershelp — `build_sam` 28%, `matching_stats_into`
16.6%, `longest_in` 15%. Read as "that is the floor of an exact algorithm", which is what I first
concluded, and it was wrong. A profile says where time goes. It does not say that **the inputs are
overwhelmingly repeats of each other**:

| level | measured |
|---|---|
| files | 51 550 → **7 543 distinct** (85.4% dup) |
| name groups | 43 504 groups holding **47 733 distinct canonicals** between them |
| definitions in a group | 368 962 → **47 733 distinct** (87.1% dup) |
| converge views | 217 980 → **29 788 distinct bodies** (86.3% dup) |
| type-3 functions | 214 040 → **29 519 distinct** (seq, name) (86.2% dup) |

Every pass was paying for that redundancy, and paying quadratically. Each now works over the
distinct inputs and expands the answer back.

## Per pass

**`scan` — one parse per distinct file content.** A definition is a function of its source and where
in it the definition sits; the path is recorded, never read. So a twin's definitions are a clone with
the path swapped, at the cost of a clone instead of a parse.

Skipped when `lenses` is requested. `Frontend::scan` is handed the whole file set and the lens kind
is the one whose unit is defined *across* it — "how this definition is used elsewhere" is counted
over the files the scan was given. Thinning that list drifted lens thickness by ±0.01 on four
clusters. Every other kind is a function of one file.

**`pass1-name` — cluster the distinct canonicals.** Exact: two identical strings have an RO ratio of
exactly 1.0, so they always join and can never lower a cluster's minimum. A group spelling **one**
canonical needs no clustering at all — and most groups are that, which alone took suffix-automaton
construction from 26% of the run's CPU to 8.7%.

Two representatives per canonical, first and last, not one. **RO is asymmetric** — the recursion
indexes one side — so a canonical occurring at several positions contributes *both* orientations of
a pair and the group reports the lower. One representative reported `min_sim` ≈0.005 high on four
clusters with membership unchanged. `x → y` is realizable iff `first(x) < last(y)`, which the two
survivors still say. Contiguous occurrences need only one: nothing interleaves with them, so no
second orientation exists.

**`converge` — tokenize once, then index by body.** `Renaming::accepts` — "do these two lines
parameterized-match" — was **71% of the pass's CPU**, `tokens` alone 54%, because the block walk
re-lexed the same lines for every candidate pair and there are millions. Tokenizing each body once
took `tokens` to 7.8%.

Then: number the bodies, and index everything derived from a body by that number — tokens, key
multiset, shape bag, first-line-per-shape. Memoize the seed walk on `(body, position)` twice over,
and the seed weighing and the shape/jaccard evidence on the body pair. `subjects` deliberately stays
per view: two definitions can spell the same body and still reach different modules, so nothing keyed
on a body may consult it. `views` and the corpus counts run in parallel, interning still in order.

**`type-3` — join over distinct `(sequence, name)` pairs.** The IDF stays over **all** functions —
`df` is how many functions contain a line, a property of the corpus, and thinning it would reweight
every vector. Sound because two functions agreeing on both keys are indistinguishable to everything
below: same row and norm, same name verdicts, same byte-identical rejection. A representative that
joins nothing expands to a group sharing one name, which the caller already drops. Also replaces a
per-function row build that was quadratic in a function's distinct lines.

**`discovery` — walk and route in parallel.** Stat'ing the tree was 10% of CPU on one thread. The
file set is collected into a set, so its order is not observable; a sorted deduplicated vector
iterates in exactly the order the `BTreeSet` did.

**`render` — one buffer.** A report this size is a million-odd lines, and each was an allocation
whose only purpose was to be copied into a `join` and dropped.

## Results

Paired run, same corpus, both binaries back to back:

| phase | before | after | |
|---|---:|---:|---:|
| pass1-name | 21 424 ms | 1 198 ms | **17.9×** |
| pass2-xname | 623 ms | 127 ms | 4.9× |
| pass5-converge | 27 061 ms | 6 770 ms | 4.0× |
| pass3-type3 | 934 ms | 396 ms | 2.4× |
| discovery | 645 ms | 326 ms | 2.0× |
| scan | 2 615 ms | 1 348 ms | 1.9× |
| render | 606 ms | 532 ms | 1.1× |
| **whole run** | **50.9 s** | **11.0 s** | **4.62× ± 0.38** |
| **CPU (user)** | **365 s** | **26.5 s** | **13.8×** |

Inside converge: seed-stmt 14 532 → 2 335 ms (6.2×), views 1 408 → 386 ms, corpus 720 → 272 ms,
subject seeding 768 → 448 ms, weighing 3 757 → 2 973 ms.

**Wall 4.6× against CPU 13.8× is Amdahl, and it is self-inflicted.** The pipeline was already ~8×
parallel; removing parallel work leaves the serial remainder exposed, and the main thread is now 24%
of the run's CPU. Two serial stretches were removed (discovery's set building, the content dedup's
ordered map). The rest is the "decide sequentially" half of a deliberate split the pass already
made, because which run a pair keeps must not depend on which worker finished first.

Thermal note: these runs sit on a warm machine, and the longer baseline suffers more from that. The
honest range for `pass1-name` is **15–19×** across runs. The CPU figure barely moves with
temperature and is the one to quote.

## Verified rather than assumed

Against a binary built from `main`, over three trees:

- **byte-identical in ten modes** — default report, `--json`, `--show-info`, converge, converge
  uncapped (`--converge-top 0`, a 39 MB ranking), converge JSON, patternology, lenses, `--calibrate`,
  `--no-type3`;
- `cargo test --release` **146 tests** and `cargo clippy --release --all-targets` green;
- the self-gate (`find-dup-defs crates -D @find-dup-defs.directives`) still reports 0 ERROR.

The uncapped converge ranking is the mode that matters. Converge findings are INFO-severity and the
human report hides INFO, so a converge check without `--show-info` compares the default report to
itself and always passes. Two real regressions were caught only there:

1. **The statement key is not a valid filter** for "can these lines parameterized-match".
   `_v0 _v1 _v0` and `_v5 _v6 _v7` *do* match — the first line of a run commits no mapping, so
   nothing conflicts — yet they normalize to `_s0 _s1 _s0` and `_s0 _s1 _s2`. Filtering on the key
   cut runs short and moved 100 lines of the ranking. The valid signature blanks slots instead of
   renumbering them.
2. **The RO asymmetry above**, which single-representative dedup would have shipped silently.

## One behavioural addition

`-D settings:converge-cap=N` exposes converge's seeding cap — how many places a shared statement may
occur in before the pass calls it an idiom. The work it admits is quadratic in it. **Default
unchanged at 60.**

Lowering it is *not* a free speedup, and it took two corpora to establish that:

| cap | converge, dup-heavy tree | findings lost there | findings lost, ordinary code |
|---|---:|---:|---:|
| 60 | 5 478 ms | 0% | 0% |
| 30 | 1 873 ms | 0.0% | **53.4%** |
| 20 | 1 412 ms | 0.0% | **69.9%** |

On a duplication-heavy monorepo the cap almost never binds, the finding count does not move at all,
and it looks like a free 3.9×. That is a property of that corpus. On ordinary code — a standard
library, a framework — statements genuinely occur in twenty to sixty places, and cutting the cap to
20 deletes seven findings in ten. **A knob whose cost depends on the shape of the input cannot be
priced on one shape.** Both tables are in the constant's doc comment.
