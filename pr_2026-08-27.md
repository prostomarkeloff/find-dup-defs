## TL;DR

Все существующие проходы канонизируют один текст — тело определения — и различаются лишь тем, сколько идентичности стирают. Это одна ось. Здесь добавляется вторая: **линза** проецирует то же определение на другой вопрос и выбрасывает остальное. Десять линз сшиваются в одну запись, и IDF-косинус пасса Type-3 по их фактам сам становится голосованием — новый механизм не понадобился. Опт-ин через `--kinds lenses`, дефолтный вывод и дефолтный JSON байт-идентичны.

## Что было

Два ортогональных кэша — один хранит JSONB-блоб, другой типизированные колонки, общих идентификаторов нет вообще — это одна архитектура, написанная дважды. Инструмент на них молчит:

```console
$ find-dup-defs ./cache_a ./cache_b
No cross-file duplicates.
```

Причина точная: **имя модели — свободное имя** в body-каноникале, поэтому `session.get(JsonCache, k)` и `db.get(ThumbEntry, i)` никогда не встречаются. То же самое разводит любую пару параллельных реализаций: имя вызываемого хелпера, имя SQL-константы, имя колонки.

- **Тело — не единственный текст определения.** У него есть сигнатура, декораторы, поток управления, контракт отказа, объявленные поля, места употребления — и ни одно из этого не участвовало в кластеризации.
- **Классы не доходили до cross-name и Type-3.** `CLASSES.fn_like` означает *callable*, а этот же флаг гейтит оба прохода, поэтому два класса с одинаковым телом под разными именами были невидимы.

## Что стало

`--kinds lenses` (пока только Python) добавляет десять перспектив:

| линза | вопрос | что оставляет |
|---|---|---|
| `outgoing` | от чего зависит? | *множество* вызываемых, которых модуль не вводил |
| `effects` | какой протокол ведёт? | те же вызовы в *порядке* вызова |
| `control` | как ветвится? | скелет if/for/while/try/return/raise с вложенностью |
| `failures` | как отказывает? | типы бросаемых и ловимых исключений |
| `resources` | что держит открытым? | контекстные выражения `with` |
| `signature` | какой контракт предлагает? | форма арности и имена аннотаций — что *есть*, а не чего нет |
| `decorators` | какую роль играет? | имена декораторов |
| `schema` | какую форму объявляет? | типы колонок и их опции, как неупорядоченное *множество* |
| `scope` | что делает тело? | тело со стёртыми именами, которые ввёл модуль |
| `use` | как с ним обращаются? | statements в других местах дерева, упоминающие его |

Результат на том же корпусе:

```console
$ find-dup-defs ./cache_a ./cache_b --kinds lenses
DUPLICATE LENSES [WARNING]: cache_get/thumb_lookup   [normalized-exact, T=0.60, n=2, loc=7]
    votes[5]: control×3 effects×1 outgoing×1 scope×1 signature×1
DUPLICATE LENSES [WARNING]: cache_put/thumb_store    [normalized-exact, …]
DUPLICATE LENSES [WARNING]: cache_evict/thumb_purge  [normalized-exact, …]
DUPLICATE LENSES [WARNING]: JsonCache/ThumbEntry     [ast sim 0.76, …]
```

Ключевые свойства:

- **Голосование бесплатно.** Все десять сшиваются в одну запись, каждый факт помечен своей линзой (`control:if`, `outgoing:.commit`, `schema:col Text nullable`). IDF-косинус Type-3 по этим строкам *и есть* голос: согласие через несколько линз поднимает score, через одну — почти не двигает, а факт, общий всему корпусу (`control:return`), обнуляется весом сам, без объявления его шумом.
- **Находка сообщает, через что она найдена.** Similarity говорит, насколько близко, и никогда — *через что*. Поле `facets` в JSON, `votes[n]: …` в человеческом отчёте.
- **Вес и голоса — независимые оценки одного.** Средний thickness растёт с числом голосов (0.71 при одном, 0.79 при трёх, 0.89 при пяти, 0.92 при шести), хотя считается из корпусной IDF и о голосах не знает.
- **Опасен не молчащий канал, а канал средней частоты.** `signature` эмитила `posonly 0` / `kwonly 0` / `async 0` для каждой обычной функции — семь фактов ни о чём — и доминировала в двух третях находок, схлопывая тысячи несвязанных определений в один кластер. Теперь сообщает только то, что у сигнатуры *есть*.

## Что изменилось

### Контракт: `crates/dup-defs-core/src/types.rs`

Появился `ScanOpts` — то, что запросил вызывающий. Некоторые виды стоят настоящей работы (второй обход всех файлов), и эмитить их без спроса значило бы замедлить дефолтный прогон и напечатать секции, которых никто не просил.

```rust
pub struct ScanOpts<'a> {
    pub kinds: Option<&'a [String]>,
}
```

`Frontend::kinds` и `Frontend::scan` принимают его; `rs-canon` / `ts-canon` игнорируют. Так выбор живёт в CLI (`--kinds`), а не в боковом канале.

### Движок: `crates/find-dup-defs/src/lib.rs`

Два дополнения.

`Finding::facets` — согласие по перспективам, `(facet, общих фактов)`, сильнейшие первыми. Движок остаётся в неведении, что значат теги: он пересекает факты членов и группирует по префиксу. Тег — голое lowercase-слово до `:`, поэтому обычные строки кода (`def _fn(_v0):`, `for _v0 in _v1:`) под него не подпадают.

`Def::thickness: Option<f64>` — фронтенд, знающий экономику своей единицы, считает её сам. Дефолтная формула `volume = (n − 1) · loc` предполагает, что кластер побольше — выигрыш побольше; для профиля это инвертируется. Движок берёт минимум по кластеру и **дисконтирует согласием**, а не усредняет:

```rust
t * (AGREEMENT_FLOOR + (1.0 - AGREEMENT_FLOOR) * min_sim)
```

Редкие факты, совпавшие наполовину, — потенциал, а не находка.

### Линзы: `crates/py-canon/src/lenses.rs` (новый)

Все десять проекций плюс корпусный скоринг. Один обход AST собирает факты для всех линз сразу.

Две потребовали отдельного обращения. **`schema`** сравнивает объявления, где порядок не является смыслом, а литералы *и есть* идентичности: факты сортируются как множество, а `__tablename__`, имена индексов и таргеты FK отбрасываются — при этом сам вызов `ForeignKey` / `Index` сохраняется (что колонка на что-то ссылается — это форма, на какую именно таблицу — идентичность). Типы колонок остаются verbatim несмотря на импорт: это грамматика, на которой написана схема.

**`scope`** даёт **один** факт — отпечаток тела целиком, и только для функций. У класса тело *и есть* объявление, которое `schema` уже раскладывает по факту на поле; `scope` вернул бы его одной строкой, уникальной для каждого класса — чистый знаменатель без общего числителя, который топил реально совпадающие декларации ниже порога косинуса.

### Профили употребления: `crates/py-canon/src/uses.rs` (новый)

`use` / `usectx` / `cooc` — единственные факты, невыводимые из определения в одиночку: они живут во *всех остальных* файлах. Сборка идёт **по имени**, без резолва импортов и графа вызовов — то же допущение, которое name-gated пасс делает всегда (замер: 2435 различных имён на 2444 top-level класса в одном продакшн-дереве).

Канал разделён на три, чтобы частичное согласие было выразимо: `use:` — полный каноникал сайта, `usectx:` — вид позиции (`guard` / `loop` / `try` / `plain`), `cooc:` — вызовы, стоящие рядом. Два якоря, защищённые одинаково, но сформулированные по-разному, теперь делят `usectx`, тогда как единый каноникал сказать этого не мог.

### Канонизация: `crates/py-canon/src/canon.rs`

`Dump` получил два аддитивных режима, оба `None` у всех существующих вызовов:

- `anchor` — имя якорного определения → `_t0`, атрибуты, читаемые прямо с него, помечаются `#name#`. Атрибут якоря приходит в двух грамматиках, `X.attr` и `X(attr=…)`; помечаются обе, иначе профиль разваливается пополам.
- `scope` — имена, которые ввёл сам модуль, переименовываются везде, **включая позицию атрибута**, куда множество локалей не дотягивается.

Плюс `ClassDef` теперь обнуляет своё имя в cross-name-режиме, как `FunctionDef` делал всегда.

## Backward compatibility

Breaking changes нет.

- Kind объявляется **только когда его запросили**, поэтому список секций отчёта не меняется.
- `facets` в JSON помечено `skip_serializing_if`, поэтому дефолтный документ не меняется.
- Golden-тесты отчёта и JSON проходят без правок.
- `Frontend::scan` / `Frontend::kinds` получили параметр — это ломает сторонний фронтенд, если такой существует; внутри воркспейса все три обновлены.
